# SaveWise 个人复盘：从能演示，走向可以每天放心用

日期：2026-10-12（America/Toronto）。本文不包含真实余额、账户身份凭证或财务数据。

## 我真正要解决的问题

我开发这个 App 是为了少输入、少计算：打开就知道接下来能花多少、哪张信用卡什么时候还。之前实现了自然语言记账、双币种展示和 AI 周报，却没有先解决开始使用、账单管理、漏记恢复和数据可信的问题。

这次调整的判断标准是：我能否从今天开始；能否解释每个余额；失败时是否会写错账；别人是否能伪造我的身份。AI 能理解一句话，不等于最终写入的数据正确。

## 做了什么，为什么这么做

| 改动 | 原来的问题 | 这次的选择 |
| --- | --- | --- |
| 真实身份认证 | 前端口令和客户端 userId 不能证明身份 | 使用 Supabase Auth 验证 token，数据库从 `auth.uid()` 得到用户 |
| PostgreSQL / RLS | 用户隔离依赖代码里手写筛选条件 | 所有应用表启用 RLS，跨账户引用同时验证 owner |
| 事务记账 | 先读旧余额再保存绝对值，可能覆盖并发变化 | 写入通过事务 RPC，按用户加锁，使用增量与版本检查 |
| 幂等与恢复 | 成功后断网，用户重试可能重复扣款 | 保存请求编号和原内容，重试返回原结果；未知结果不报成功 |
| 从今天开始 | 不知道是否必须补以前的账 | 当前余额与欠款作为起始快照，排除收入和消费 |
| 独立信用卡账单 | 当前总欠款无法回答本期该还多少 | 每期保存账单金额、剩余应还和完整实际到期日期 |
| 对账与历史补录 | 覆盖余额没有记录，之后补账可能再次扣款 | 对账保存旧值、新值与说明；检查点之前补录只完善历史 |
| 分币种统计 | CAD/CNY 原始金额直接相加没有意义 | 金额按整数分保存，原币种分别统计，不伪造汇率 |
| 首页重排 | 净资产和目标进度占中心，预留学费也被当储蓄 | 现金减预留和已知应还，展示可支配金额和到期清单 |
| 减少外部依赖 | 首页经过健康检查、汇率；提交必须等 Gemini | 首页与确定性记账直接访问 Supabase，暂停 AI 功能 |
| 缓存与演示隔离 | 切换时旧响应、草稿可能残留 | 缓存按账号隔离，退出清理；演示纯本地虚构、只读 |

### 认证：公开源码不应意味着公开余额

前端代码和公开客户端 key 可以被所有人看到，不能拿它们当秘密。真正的边界是 Supabase 验证签名后的身份，以及数据库对账户归属和操作权限的检查。

本次客户端没有直接写表权限，全部修改经过受约束的函数。内部幂等回执也不向客户端开放。SDK 在浏览器管理登录会话，这不是 HttpOnly Cookie 方案；后续仍要保护前端依赖与避免 XSS，不能把认证服务当作万能保护。

### 财务：余额、消费和账单是三件事

起始余额不是收入，起始欠款不是当期消费。刷信用卡时增加消费和总欠款，还款时降低银行余额与欠款，不再记一次消费。本期剩余应还通过账单和还款分配跟踪，不能拿全部欠款代替。

银行可能调整实际到期日期，所以保存完整日期，不再推算“每月几号”。当天到期显示当天，过期仍保留逾期状态，不跳到下个月。

漏记不应该让我放弃。对账可以建立新的可信检查点，未知差额不伪造成收入或消费；以后补旧交易不会再次改变已经对好的余额。同一天的旧交易仍需要显式选择“只补历史”，这是当前最小版本的操作边界。

### 产品：可支配金额比净资产更贴近日常问题

目前的规则是：现金资产减生活/学费/储蓄预留，再减未来 30 天及逾期的未还账单。各币种分别算，避免看起来精确、实际混币的总数。

这个数字是一份基于已知数据的计划，不能保证未来所有支出都被预测。未出账消费仍保留在总欠款中，缺少账单会提示金额可能偏高。我需要先确认银行账单，再把首页数字作为花钱参考。

### 性能：这次改变路径，没有证明所有延迟已经消失

Supabase 适合这个小项目，是因为可以把登录、用户隔离和事务集中起来。性能收益主要来自缩短链路、删除必须等待的 AI 和汇率调用，而不是“换数据库一定更快”。仍需上线后量首页和提交的 p50/p95；没有付费升级，也没有测量前的性能保证。

## 已落地到哪里

- 云端项目已关联并应用 `20261013000100` 迁移，原 MongoDB 数据未删除或导入。

- 首页函数使用 STABLE 数据库快照，避免余额、账单与统计在并发下来自不同读取时点。[PostgreSQL 快照规则](https://www.postgresql.org/docs/current/xfunc-volatility.html)

- 15 项本地测试通过，覆盖虚构 A/B 隔离、回滚、部分/跨期还款、幂等、退款、对账、撤销与日期边界。
- 前后端构建及 lint 通过；添加 GitHub CI，避免以后提交破坏关键规则。
- 复查时还补了账号切换清理首次设置草稿，避免未提交余额留给下一位用户。

云端核验只读取系统目录，没有读取真实财务记录或用户列表；虚构 A/B 测试没有放到生产。验证结构正确不等于已完成真实用户登录、银行对账或多连接压力测试。

## 我学到什么

1. TypeScript 类型不是运行时校验，模型输出不能直接成为资金变动。
2. 数据库事务不能修复事务外读到的旧值；幂等也不能靠禁用按钮替代。
3. “成功”“失败”“结果未知”“保存成功但刷新失败”必须分别表达。
4. 没有记录不等于没有消费。财务产品应承认数据覆盖不足。
5. 演示应有自己的虚构数据，而不是用一个弱身份进入个人数据库。
6. README 只能描述代码和验证真正支持的行为，不应把愿景写成已经实现的功能。

## 接下来怎么用、怎么判断是否值得继续改

先创建自己的登录用户，配置托管平台的公开环境变量，用银行当前余额开始。前几天重点核对三件事：一笔消费只扣一次；部分还款同时改变总欠款与剩余应还；漏记后对账可以继续，旧账补录不重复扣款。

未来优先级：真实登录和部署验收 → 实际 PostgreSQL 并发验证与延迟测量 → 交易分页 → 可预览、去重且不重复影响余额的历史导入 → 完整月份确认。自动汇率、银行同步和 AI 暂时排后。

我需要保留一个原则：先让这份账值得信任，再增加功能。

## 2026-10-13 追加复盘：上线才是手机用户的交付

手机使用的是 Vercel 的静态构建，而不是我的本地开发服务。代码 push、数据库建表、Vercel 构建成功是不同的检查点；生产构建如果没有两个公开客户端变量，用户仍然无法登录。

这次把生产变量、重新发布和正式网址核验纳入交付，并增加缺配置即阻止构建的保护。同时从个人邀请模式调整为多人注册：前端补注册与邮件确认，云端开放注册，但仍保留邮箱确认和各用户独立 RLS。

还发现邮件是独立依赖：默认 Supabase 发信不能用于任意用户邮箱。必须配置自定义 SMTP，才能完成其他用户实际收信和注册的验收；不能为了赶上线而关闭邮箱验证。相关密码只留在服务端，不进入前端或 Git。
